# claude-pane-statusline

![license](https://img.shields.io/badge/license-MIT-blue) ![platform](https://img.shields.io/badge/platform-Windows-0078D4) ![dependencies](https://img.shields.io/badge/dependencies-0-brightgreen) ![binary](https://img.shields.io/badge/binary-312%20KB-orange)

**Tell your Claude Code panes apart.** Run several sessions side by side and every one looks
identical. This gives each pane a line that says what it is working on and whether it is
waiting on you.

![Two statusline examples: a working pane with issue chip and gauges, and a red-caret pane waiting for input](preview.svg)

```
 ● │ ⌂ my-repo │  main │ #70 │ ✦ Fix instance budget test failures │ Opus 5 │ ▰▰▱▱▱ 42% │ ⧖ 7d 78%
```

| Segment | Meaning |
|---|---|
| `●` / `❯` | Green dot: Claude is working (with elapsed time). Bold red caret: the pane is **waiting on you** — a finished turn, a permission prompt, or a question. |
| `⌂ my-repo` | Folder / worktree the session runs in (blue = git repo, grey = plain folder). |
| ` main` | Git branch. Hidden when the folder name already contains it (common for worktrees). |
| `#70` | Claimed issue chip — [optional](#optional-issue-chip). |
| `✦ title` | **Live task label** — a ≤6-word summary of the session's prompt history, regenerated by Haiku after every substantive prompt. The `✦` pulses while a new title is generating. |
| `Opus 5` | Model. |
| `▰▰▱▱▱ 42%` | Context usage — green, yellow at 60%, red at 80%. |
| `⧖ 7d 78%` | Rate-limit windows (5h/7d) — shown only at ≥75%, red at 90%. |

## Why

- **Panes label themselves.** Not just a folder name — an actual summary of what that
  session is doing, so you can find the one you care about at a glance.
- **It tells you which pane is blocked on you.** Across six panes, that is the whole game.
- **It is effectively free.** A render costs less CPU than the empty `bash` wrapper Claude
  Code puts around *any* command, and an idle pane costs exactly zero. See
  [Performance](#performance).
- **One 310 KB binary, zero dependencies.** No node in the hot path, no runtime, no crates.
- **Extensible from anything.** The whole system talks through small files in one
  directory — [that directory is the API](#extending-it).

## Requirements

- A terminal with truecolor and powerline glyphs (Windows Terminal with Cascadia, or any
  Nerd Font terminal)
- A Rust toolchain to build
- The `claude` CLI installed and logged in — only for the Haiku task labels, billed to
  whatever login it has (a Claude subscription works, no API key needed). Without it
  everything else still works and labels fall back to the built-in session name.
- `node` on PATH — **only** for `session-task.js`, the summarizer. Nothing in the
  per-render path needs it.

**Platform:** developed and measured on Windows 11, and everything here about Git Bash,
conhosts and abandoned renders is Windows-specific. The crate compiles on other platforms
(stray collection is `cfg`-gated to Windows, the rest is portable) but is **untested** on
macOS and Linux, and the setup instructions assume Windows paths.

## Install

**Easiest: let Claude do it.** Clone the repo, open Claude Code, and say:

> install the statusline from this repo per the README

[Instructions for the installing agent](#for-an-installing-agent) are at the bottom.

**Manually:**

```sh
cargo build --release      # -> target/release/statusline.exe
```

Copy `target/release/statusline.exe` and `session-task.js` into `~/.claude/`. They locate
each other, and `session-tasks/`, relative to their own position — nothing inside them
needs editing, but they must sit in the same directory.

Then merge this into `~/.claude/settings.json`, replacing `<HOME>` with your absolute home
directory. Preserve everything already in the file; if you already have `hooks`, append to
each event's array rather than replacing it:

```json
{
  "statusLine": {
    "type": "command",
    "command": "\"<HOME>/.claude/statusline.exe\""
  },
  "hooks": {
    "UserPromptSubmit": [
      { "hooks": [
        { "type": "command", "command": "node \"<HOME>/.claude/session-task.js\"", "async": true, "timeout": 90 },
        { "type": "command", "command": "\"<HOME>/.claude/statusline.exe\" state working", "async": true, "timeout": 10 }
      ] }
    ],
    "PostToolUse":  [ { "hooks": [ { "type": "command", "command": "\"<HOME>/.claude/statusline.exe\" state working", "async": true, "timeout": 30 } ] } ],
    "Stop":         [ { "hooks": [ { "type": "command", "command": "\"<HOME>/.claude/statusline.exe\" state waiting", "async": true, "timeout": 10 } ] } ],
    "Notification": [ { "hooks": [ { "type": "command", "command": "\"<HOME>/.claude/statusline.exe\" state waiting", "async": true, "timeout": 10 } ] } ],
    "SessionEnd":   [ { "hooks": [ { "type": "command", "command": "\"<HOME>/.claude/statusline.exe\" state clear", "async": true, "timeout": 10 } ] } ]
  }
}
```

That is it — `settings.json` is re-read live, so running sessions pick this up without a
restart. Note there is no `refreshInterval`; leaving it out is deliberate ([why](#tuning)).

Colors are Tokyo Night truecolor, defined as one block of constants at the top of
`src/render.rs` — see [reskinning](docs/extending.md#reskinning).

**Tests**

```sh
cargo test                       # 36 unit tests
.\tests\reaper-integration.ps1   # ~90s, Windows only
```

The unit tests cannot cover the part of stray collection that matters, so the integration
script creates genuinely suspended processes with `CreateProcess(CREATE_SUSPENDED)` and
never resumes them — reproducing the upstream bug rather than simulating it.

## How it works

- **`statusline.exe`** renders the line. Claude Code pipes it session JSON on every update;
  it reads the branch straight out of `.git/HEAD` and reads the small state files below.
- **`statusline.exe state working|waiting|clear`** is the same binary as the attention-state
  hook, so the hot path and the hook can never drift apart. Prompt submitted or tool
  completed → `working`; turn finished or notification → `waiting`; session ended →
  cleared. `PostToolUse → working` is what turns a pane green again after you approve a
  permission, and it is the second-hottest path after the render — the common case
  ("already working") writes nothing and exits.
- **`session-task.js`** runs on every prompt (async, so you never wait on it). It keeps your
  last 20 substantive prompts in `<id>.history`, asks Haiku for a ≤6-word title for the
  whole arc, and writes `<id>.txt`. Prompts starting with `/` or shorter than 15 characters
  never change the label. If the call fails, the previous label stays.
- **State lives in `~/.claude/session-tasks/`** as small per-session files. Anything older
  than 7 days is pruned automatically.
- **Once a minute, whichever render is running also collects abandoned renders**
  ([why](#leaked-render-processes-windows)). No scheduled task, no background service —
  nothing here runs when Claude Code isn't.
- The summarizer child sets `RTS_TASK_SUMMARIZER`, which makes every hook above exit
  immediately. That guard prevents infinite hook recursion — don't remove it.

## Optional: issue chip

If a tool call runs `issue.ps1 claim <n>` (an issue-claiming convention from the repo this
was built in), the pane pins that issue: an orange `#n` chip appears, `gh` fetches the
title, and Haiku titles anchor to that issue until `issue.ps1 done <n>`. If your repo has
no such script this never triggers — or adapt `issue_invocation` in `src/state.rs` to your
own command.

## Tuning

- **`refreshInterval` is deliberately absent.** It is in *seconds*, it stacks *on top of*
  event-driven updates rather than replacing them, and it has no default — so omitting it
  means idle panes never re-render at all. Add it back only if you want a smoother spinner,
  knowing you buy it with a render on every pane every N seconds forever. There is no way
  to make it conditional on state.
- Label length is capped at 60 characters, trimmed at a word boundary.
- Testing from PowerShell 5.1? Its pipes prepend a BOM; the parser strips it deliberately.

## Performance

Claude Code re-runs the statusline as a fresh process on every update, so a process spawn is
the unit of cost — which is why the renderer is a native binary rather than a script.

| per render | node (before) | native |
|---|---|---|
| Wall clock | 366 ms | **9.7 ms** |
| CPU (whole tree) | 309.4 ms | **135.9 ms** |
| Working set | 47 MB | **4.3 MB** |

For scale, `bash -c "exit 0"` costs **140.6 ms** of CPU — what Claude Code pays to run *any*
command on Windows. **A render now costs less than the empty wrapper around it**, and an idle
pane costs nothing at all. The only measurable cost left is the Haiku summarizer, ~8.8 s per
substantive prompt, and only while it generates.

→ **[Full measurements, methodology, and two dead ends](docs/performance.md)**

## Leaked render processes (Windows)

Claude Code's spawner sometimes creates a render child `CREATE_SUSPENDED` and abandons it
before resuming: 0 CPU time, one suspended thread, never executed an instruction. No code
inside such a process can rescue it, in any language. 1,083 of them once held 33 GB.

The binary collects them itself — once a minute, whichever render happens to be running
sweeps for abandoned copies of itself. No scheduled task, no background service, no extra
process, and nothing runs when Claude Code isn't.

→ **[Signature, safety rules, and how it is tested](docs/leaked-processes.md)**

## Extending it

The whole system talks through plain files in `~/.claude/session-tasks/`, keyed by session
id — **that directory is the API**. Write `<id>.txt` and the label changes; write
`<id>.issue` and the chip appears. Any hook, in any language, can drive it.

→ **[File reference, worked examples, and reskinning](docs/extending.md)**

## For an installing agent

You are installing one self-contained binary plus one node script, and registering them in
the user's **user-level** `~/.claude/settings.json`. Nothing here touches a project.

1. Check the requirements. If `claude -p` is unavailable, install anyway and tell the user
   labels will fall back to the built-in session name.
2. Run `cargo build --release`, then copy `target/release/statusline.exe` and
   `session-task.js` into `~/.claude/`. They must land in the same directory.
3. Back up `~/.claude/settings.json`, then merge the snippet from [Install](#install) —
   read the existing file first and preserve everything in it, especially existing `hooks`
   entries (append to an event's array, never replace it). Use the user's real home
   directory, absolute, in the platform's own path style.
4. Verify before declaring success:
   - Pipe `{"model":{"display_name":"Test"},"workspace":{"current_dir":"<any git repo>"}}`
     into `~/.claude/statusline.exe` → an ANSI line naming the repo folder and branch.
   - Pipe `{"session_id":"t1","prompt":"add a settings page with theme toggle"}` into
     `node ~/.claude/session-task.js` → within ~15 s `~/.claude/session-tasks/t1.txt`
     contains a short title (proves the `claude -p` call works).
   - Pipe `{"session_id":"t1"}` into `~/.claude/statusline.exe state waiting` →
     `~/.claude/session-tasks/t1.state` contains `waiting`.
   - Delete the `t1.*` test files and confirm `settings.json` still parses as JSON.
5. Nothing to register for leaked-process cleanup — the binary collects its own strays. If
   the user has a `StatuslineReaper` scheduled task from an older install, remove it with
   `Unregister-ScheduledTask -TaskName 'StatuslineReaper' -Confirm:$false`.
6. Tell the user it is live immediately — `settings.json` is re-read without a restart.

## Contributing

Issues and pull requests welcome. A few things worth knowing first:

- **Run the tests.** `cargo test` for the unit tests, plus `.	estseaper-integration.ps1`
  on Windows — the unit tests cannot cover the part of stray collection that matters.
- **Keep `[dependencies]` empty.** Every crate is build-time and supply-chain surface for a
  program that parses one small JSON object and prints one line. If something genuinely
  needs one, make the case in the PR.
- **Measure claims about cost.** Per-process CPU excludes children and wall clock is noisy
  on a busy machine; both mislead here, and both misled me. See
  [measuring this yourself](docs/performance.md#measuring-this-yourself).
- **Non-Windows patches are welcome but untestable by me.** The crate compiles elsewhere and
  nothing more is promised — say in the PR if you have actually run it.

## Support

Bugs and questions → [GitHub issues](https://github.com/CheersLoveDani/claude-pane-statusline/issues).

Two things that look like bugs and are not:

- **The statusline vanishes entirely.** Usually `statusline.exe` is not where
  `settings.json` says it is — Claude Code renders nothing rather than complaining. Pipe
  `{}` into the path in your settings and see whether you get a line back.
- **Labels never update.** The `claude` CLI is not logged in. Everything else keeps working
  and the label falls back to Claude Code's built-in session name.

## Uninstall

Delete `statusline.exe`, `session-task.js` and `~/.claude/session-tasks/`, then remove the
`statusLine` block and the six hook entries from `~/.claude/settings.json`. There is no
scheduled task or background service to unregister. (If you installed a version from before
stray collection moved into the binary, also run
`Unregister-ScheduledTask -TaskName 'StatuslineReaper' -Confirm:$false`.)
